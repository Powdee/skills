# /design-profile — learn this repo before designing in it

The rest of this pack ships placeholders: `<ui-package>`, `<check-cmd>`,
`<ui-barrel>`. This skill replaces them with facts, discovered from the repo in
front of you and confirmed by a human, then writes them somewhere the other
skills can read.

**Run it once when adopting the pack.** Run it again when the repo moves.

## STEP 1 — Probe

```bash
python3 <skill-dir>/scripts/probe-repo.py --root .
```

Python 3 stdlib only, no install, read-only. It reports and decides nothing.
Add `--json` if you want to post-process it.

It answers:

| Question | How it decides |
|---|---|
| Where do shared components live? | the directory holding the most `*.stories.*` |
| What is the export barrel? | `index.ts`/`index.tsx` files over 2 KB in that package |
| Where are the tokens? | every `.css` declaring ≥5 custom properties, biggest first |
| What is the styling stack? | dependencies across every `package.json` |
| Where is Storybook? | `.storybook/main.*` |
| What is the check command? | root `package.json` scripts matching lint/typecheck/test/check/storybook |
| Do components here have tests? | stories vs tests counted **inside that package** |
| How are stories titled? | the `title:` field's first segment, ranked |
| Are there written conventions? | `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md` |

## STEP 2 — Read what it found, and doubt it

The probe counts; it does not understand. Four findings mislead often enough to
check every time:

**More than one token file.** Two files with overlapping custom properties may
be a duplicate that must be kept in sync by hand, a per-app override layer, or
one dead file nobody deleted. The probe flags the count; only a person knows
which. Get this wrong and every later token mapping points at the wrong file.

**The testing convention.** A package reporting more tests than stories does not
mean "write tests here". Many repos test the *logic* in a package while its
*components* carry
only stories. Check what the component files next to your target actually have,
not the package-wide ratio.

**The biggest package is not always the right one.** A repo can keep primitives
in one package and composed domain components in another. If the probe's top two
are close, that is a real split, not noise.

**A recognised stack is not a used stack.** `cva` in `package.json` proves it is
installed, not that it is the convention. Open two components in the target
package and confirm the pattern before writing it into the profile.

## STEP 3 — Read a real component

Numbers cannot tell you house style. Open **two** components in the shared
package — one simple, one with variants — and read off:

- how variants are expressed (a variant map, props, class strings)
- how classes are composed and merged
- whether tokens are referenced as CSS variables, utility classes, or theme keys
- what a story file looks like: title, args, `argTypes`, decorators
- whether stories carry play functions or visual-diff hooks

Whatever you find here is the answer, regardless of what any skill says.

## STEP 4 — Confirm the ambiguities

Put the findings to the human as a short list, with the probe's evidence
attached, and ask about anything the probe could not settle. Prefer specific
questions over "does this look right":

- "Two token files, `A` (96 tokens) and `B` (87). Which is canonical, and do
  they have to stay in sync?"
- "Components in `<pkg>` have both stories and tests. For a **new**
  presentational component, do you want tests?"
- "`<check-cmd>` — is `npm run lint && npm run typecheck` the right gate, or is
  there a single command?"

## STEP 5 — Write the profile

Write `.claude/design-profile.md` at the repo root. Keep it short; it is read
before every design task, and a long one gets skimmed.

```markdown
# Design profile

Generated by /design-profile on <date>. Re-run when the repo moves.

## Where things live
- Shared components: `<path>` (<n> stories)
- Export barrel: `<path>`
- Storybook config: `<path>`
- Token source of truth: `<path>` (<n> tokens)
- Other token files: `<paths>` — <in sync by hand / per-app overrides / dead>

## Stack
<Tailwind + cva + Radix / CSS Modules / …>, confirmed by reading `<file>`.

## Conventions
- Story titles: `<Root>/<Component>`; the roots in use are <list>.
- Tests in the shared package: <yes / no / logic only>.
- Check command: `<cmd>`
- Storybook command: `<cmd>`
- Written conventions: `<file>` — read it before STAGE 4.

## Token vocabulary
Colour families: <list>. Radius: <list>. Spacing: <list>. Type: <list>.
Pull live with `<command>`; never from memory.

## Open questions
- <anything the probe could not settle and nobody has answered yet>
```

Then tell the human where it is and what is in it.

## Re-running

On a second run, diff the new findings against the existing profile and report
only what changed. A moved token file or a renamed package silently breaks every
later token mapping, and the profile is the only place that would notice.

Do not rewrite a profile a human has edited without showing the diff first —
hand-written lines in `## Open questions` and `## Conventions` are usually the
most valuable content in the file.

## What this skill will not do

It will not invent a convention the repo does not have. If the probe finds three
competing focus-ring colours or two token files nobody can explain, the profile
records that as an open question. A stated convention that is actually a guess
is worse than a blank, because everything downstream treats it as settled.

## Checklist

- [ ] Probe run against the real repo root.
- [ ] Multi-token-file finding resolved by a human, not assumed.
- [ ] Testing convention checked at component level, not package ratio.
- [ ] Two real components read before recording the stack.
- [ ] Ambiguities asked as specific questions.
- [ ] `.claude/design-profile.md` written, short, with open questions kept.
- [ ] Nothing invented; unknowns recorded as unknown.
